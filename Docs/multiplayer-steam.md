# Multiplayer — Steam Sessions & Transport

**MUST READ before touching `UCatGameInstance`, net drivers/transport config, session UI, or packaging for a multiplayer test.** Split out of CLAUDE.md on 2026-08-16 — text unchanged. ## Steam Sessions (`UCatGameInstance`)

C++ session backend only — no UI or `ServerTravel` here. Uses Online Subsystem Steam on the project's **real AppID 4567540** (depot 4567541) — *not* 480; the old "480 dev mode" claim was stale and is corrected here and in the two `CatGameInstance.cpp` comments. `UCatGameInstance` is assigned directly in DefaultEngine.ini — there is **no Blueprint GameInstance subclass**. SteamPipe upload pipeline exists and has been used (`PackageDevelopmentBuild.bat` → `SteamPipeScripts\app_build_4567540.vdf`; "setlive" is empty = set live by hand in the Steamworks web UI).

**Transport = the `SteamSockets` plugin (fixed 2026-08-07 after a 3-month invisible failure).** Symptom: hosting, lobby discovery and join all reported success, then every cross-account join died in ~3 ms with `PendingConnectionFailure`. Cause: `GameNetDriver` pointed at `OnlineSubsystemSteam.SteamNetDriver`, a class UE 5.7 **moved** into the (disabled-by-default) `SocketSubsystemSteamIP` plugin — so it did not resolve, and `CreateNamedNetDriver` (`UnrealEngine.cpp:14644`) loads `DriverClassNameFallback` via `StaticLoadClass(..., LOAD_Quiet)` with **no warning of any kind**. Every build silently ran raw `IpNetDriver`, which can neither listen on nor connect to the `steam.<SteamID64>:7777` P2P URLs lobby sessions advertise (lobby sessions have no host IP, so `GetConnectStringFromSessionInfo` always returns the P2P form). Three things to know, each of which cost a round:
- **Class paths in `NetDriverDefinitions` MUST be the fully-qualified `/Script/` form.** `SteamSockets.SteamSocketsNetDriver` does **not** resolve; `/Script/SteamSockets.SteamSocketsNetDriver` does. The trap is that the short form *does* work for some core modules (`OnlineSubsystemUtils.IpNetDriver` resolves fine), so a short-form config looks correct and fails silently. Same rule applies to `NetConnectionClassName` — a short-form value there overrides a correct `BaseEngine.ini` default and only breaks when a client actually connects, not at listen time.
- **`bUseSteamNetworking=false` is required**, not optional. Left at the engine default (true), SteamSockets registers as the process-**default** socket subsystem. `SteamSocketsNetDriver` doesn't care (it asks for its subsystem by name), but `IpNetDriver` takes the default — so any fallback to IpNetDriver gets handed Steam sockets, tries to bind the local SteamID, fails `setsockopt SO_BROADCAST`, and **the host cannot listen at all**. That converts a silent degradation into a hard failure. Note the LAN beacon is *not* affected (it takes `PLATFORM_SOCKETSUBSYSTEM` explicitly) — checking only the beacon and concluding the flag was safe is exactly the mistake that shipped this.
- **Steam transport cannot be tested in the editor**, by design (`SteamSocketsModule.cpp:15` gates init on `IsRunningDedicatedServer() || IsRunningGame()`); PIE always falls back to IpNetDriver and is unaffected by all of the above. Verification = packaged builds. A packaged host can be smoke-tested headlessly in ~30 s without a second machine: `CatVentures.exe /Game/Maps/TestMap_02?listen -log -nullrhi -unattended -nosplash`. Also: only ONE instance per machine can init Steam (`bInitServerOnClient=true` makes the client grab the Game Server API too), so a single-box two-instance Steam test is impossible — the second instance falls back to the NULL subsystem. For direct-IP testing use `-nosteam` on both ends (SteamSockets' address parser rejects dotted IPs).

**Re-verified on UE 5.8 (2026-08-15), packaged Development build.** `SteamSockets` lives at `Engine/Plugins/Runtime/Steam/SteamSockets` in **both** 5.7 and 5.8 — the plugin did not move and `/Script/SteamSockets.SteamSocketsNetDriver` still resolves. A headless packaged host logged `Class=SteamSocketsNetDriver`, `SteamSockets: Initializing Network Relay`, `Now tracking socket … for addr <SteamID64>:7777`, `started listening on 7777`, and `RelayNetworkStatus: avail=OK config=OK anyrelay=OK` — 0 errors, and the only two warnings (no Steam stats configured; one transient SDR config fetch that retried) also appear in the working 5.7 reference log. **The 2-PC cross-account join then PASSED on 5.8 (2026-08-16), both directions** — see *Session lifecycle* below for the pre-existing bug that test exposed. Also confirmed still true: `steam_appid.txt` is **not** in the staging manifest — the Development runtime writes it from `SteamDevAppId`, so the gap remains real for Shipping.

**`[Net] NetDriver created  Def=... Class=... Obj=...`** is logged from `UCatGameInstance` (bound to `FWorldDelegates::OnNetDriverCreated`, before the OSS early-returns so it still reports under `-nosteam`). It exists specifically because the fallback is silent, and it covers the client's `PendingNetDriver` too. `Class=IpNetDriver` on a Steam build means the fallback fired. `WarnIfNotSteam` additionally warns when a non-LAN Host/Find runs on a non-Steam OSS. `-ForceLAN` on the command line sets `bForceLANMatch` (packaged builds have no CDO to tick); pair with `-nosteam`.

Known/deferred: `steam_appid.txt` never actually stages into the archive (the `AdditionalNonUFSFiles` entry matches nothing) — harmless for non-Shipping builds, which auto-write it from `SteamDevAppId`; real for Shipping. `BuildUniqueId` mismatch silently hides sessions between different builds (engine drops them with only an engine-log warning), so 2-PC tests must use the same archive on both ends. Test protocol: `Saved/.Aura/plans/steam-mp-test-protocol.md`.

- BP-callable: `HostSession(MaxPlayers, bIsLAN)`, `FindSessions(MaxResults, bIsLAN)`, `GetFoundSessions()`, `JoinFoundSession(Result)`. Each completes via a BlueprintAssignable delegate (`OnHostSessionResult`, `OnFindSessionsComplete`, `OnJoinSessionResult`).
- **Re-hosting**: `DestroySession` is async — `HostSession` defers the create into `HandleDestroySessionComplete` when a session already exists. Never call `CreateSession` immediately after `DestroySession`. The same rule applies to **joining**, and to every other caller — see *Session lifecycle*.
- **Join → travel**: on success, `HandleJoinSessionComplete` resolves the connect string and calls `PC->ClientTravel(...)`, then broadcasts `OnJoinSessionResult` with the URL. BP must NOT re-issue `ClientTravel` — that caused a false "JOIN TRUE" with no actual travel.
- **Search key**: UE 5.7 OSS Steam routes `FindSessions` to the Steam lobby list only when the **`SEARCH_LOBBIES`** key (`Online/OnlineSessionNames.h`, value `"LOBBYSEARCH"`) is set. The old `SEARCH_PRESENCE` key was removed from the engine; hand-rolled FName strings silently fall through to the internet *server* query and find nothing. Always use the engine macro.
- Session settings use `bUsesPresence`, `bUseLobbiesIfAvailable`, `bAllowJoinViaPresence` (overlay "Join Game"). Overlay invites route through `HandleSessionUserInviteAccepted` → `JoinFoundSession`.
- `bForceLANMatch` is a debug-only toggle that forces the LAN path. Single shared session name: `"CatVenturesSession"`.
- **Session UI** lives in `WBP_MainMenu` (host: `HostSession` → on success → `Open Level TestMap_02?listen`; find: busy-guard + timeout safeguard + throbber → `FindSessions(20)`; rows in `WBP_ServerRow` call `JoinFoundSession`). The **return-to-menu** buttons live in `WBP_RaidScoreboard` and call `LeaveToMainMenu` — see *Session lifecycle*.

## Session lifecycle

**Every session state transition has to be routed through `UCatGameInstance`, because the session outlives the map.** This section exists because a 2026-08-16 2-PC test found four separate defects that all presented as one symptom — "the second join hangs on *Joining* forever" — and the fix is only obvious in hindsight. Fixed in `e6d9fec`, verified on 2 PCs both directions.

**`DestroySession` is async, there is exactly ONE completion delegate, and four different callers now need it.** `HandleDestroySessionComplete` therefore dispatches on **`ECatPendingSessionAction`** (`None`/`Host`/`Join`/`LeaveToMenu`/`Quit`), not a bool — the bool worked while only re-host and quit existed, and a third boolean was precisely where a missed check would silently re-create a session someone was trying to leave. Two rules for adding a fifth caller:
- **Consume the action before dispatching.** Every branch can re-enter the session system (a join issues `JoinSession`, a host issues `CreateSession`), so a stale action left set would misroute the *next* destroy that completes.
- **Decide deliberately whether your branch honours `bWasSuccessful`.** `Quit` and `LeaveToMenu` ignore it — the player asked to leave and a failed teardown must not strand them; worst case is a lobby Steam expires on its own. `Join` must honour it, because joining with the old session still registered is exactly the failure the destroy exists to prevent.

**`JoinSession` fails SYNCHRONOUSLY with `UnknownError` if a session already exists under `SESSION_NAME`.** Identical trap to the re-host bug, one function over. `JoinFoundSession` defers into the destroy callback the same way `HostSession` does; the real call lives in `JoinSessionInternal` so the direct and deferred paths cannot drift. The symptom is nasty because it looks *directional* — whoever hosts next is saved by the host path, whoever joins next is not — which reads as "joining is broken on that PC."

**Returning to the main menu MUST go through `LeaveToMainMenu()`.** Not `Open Level`, not `Host_ServerTravel`. Both of those were in use and both were wrong:
- A bare `Open Level` travels fine but leaves the session registered, arming the `UnknownError` above for the next join.
- `Host_ServerTravel` carries **`?listen`** through the travel. The outgoing SteamSockets listen socket is not released before the new net driver binds, so it dies on `Cannot create listen socket. Already have a listen socket on P2P vport 7777` → `NetDriverListenFailure` → `LoadMap: failed to Listen` → fallback to `Map_Title?closed`. The machine ends up on the title screen with a dead net driver **and** a session it is still advertising but can no longer serve. **A menu is never a server** — travel absolute, with no options.
- `Host_ServerTravel` is still correct for **Play Again**, where the host legitimately stays a listen server.

**A UI element that disables itself pending an async result owns restoring itself.** `WBP_ServerRow` set "Joining…", disabled its button and bound nothing — that unrestored row *was* the visible hang, and it survived every correct `OnJoinSessionResult(false)` broadcast the C++ made, because MainMenu's `RestoreUI` does not reach into the rows. Failure now clears the stale list and reports it, and the row arms a 10 s `Set Timer by Function Name` → `RestoreJoinButtonOnTimeout` for the case where no result arrives at all (the destroy deferral adds a real async gap).

**Regression sequence** (the only one that catches this class — a plain host/join pass will not): play a full match → **both** machines return to the menu → the **other** machine hosts → join. Then swap. Run it on a **freshly packaged** build; the archive is what a 2-PC test executes and it does not rebuild itself. Healthy log shape on the returning machine is `LeaveToMainMenu — live session found, destroying before travel` → `HandleDestroySessionComplete … Action=LeaveToMenu` → `Travelling to the main menu (Map_Title)` with **no `??listen`**, and the subsequent `HostSession` should reach `CreateSession` *without* needing its destroy-first path — the guards are belt-and-braces once the leave path is doing its job.
