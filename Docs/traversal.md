## Traversal (`UCatTraversalComponent`) — MANTLE LIVE (mechanics, 2026-07-22)

The traversal component (per the LOCKED plan `Saved/.Aura/plans/traversal-verbs.md`: mantle → wall bounce → vertical scramble → fence trot → curtain climb) owns every traversal verb's movement takeover — **the ONE CMC apply/restore point for traversal** (the CatBase-growth-watch decision). V1 ships the **mantle** on placeholder anim (mechanics-first doctrine): airborne + input held + chest probe (wall, reach 45) + lip probe (floor **25–70 uu above the capsule bottom** — 105 shipped first; Sean's log histogram read 103+ catches as superhero, 64–74 as cat) + headroom check (**a capsule fit test at the landing pose since 2026-08-11 / BB-15** — it was a single centre-line ray that tested neither the radius nor the capsule's lower half, so a narrow ledge, a pillar beside the landing spot or a low side overhang all passed; shrunk 1 uu so the deliberate 2 uu float above the lip can't graze into a false reject) → `MOVE_Flying` takeover on a vertical-first curve (SmoothStep Z 0–0.55, XY 0.35–1; duration 0.35 + height×0.0015; exit velocity 150 — no baked lunge). **EndMantle restores `MOVE_Falling`, NEVER Walking** — the target floats the capsule ~2 uu over the ledge so the CMC processes a REAL landing (full `Landed()` path: phase flow, cushion kick, foot-IK snap); a direct Walking switch skips `Landed()` and parked `JumpPhase` at Fall forever (the stuck-fall-pose bug — only descent-phase catches stuck, hence flaky repro; the jump SM's `Fall` case also gained the Launch/Apex-style grounded-safety → `None`, which protects every future mode-switch verb). MP = the grab pattern: owner detects + drives, `Server_StartMantle(Start, Target)` mirrors, the server drives its own copy deterministically from the same params (no progress streaming); proxies read the pawn's replicated `bGoMantle`/`MantleProgress` (COND_SkipOwner). `Move()` input is suppressed while mantling; the component is a `friend` of `ACatBase`. Per-mantle log line (ledge height + duration, LogCatVentures) = the clamber-clip authoring spec; `MantleProgress` PawPrint channel.

**Clamber clip + Mantle state — SHIPPED 2026-07-24, Sean-accepted as a stub ("mechanically working as I would expect… fine for now").** `A_Cat_Mantle_Clamber` (`/Game/Drafts/M5`, 0.5 s / 16 keys / 30 fps, root track flat) → ABP `Mantle` state, Sequence Evaluator scrubbed by `MantleProgress × 0.5`. Zero new C++ — `bGoMantle`/`MantleProgress` already existed; the ABP just gained the two variables + EventGraph sets (appended after `Set JumpRiseProgress`). Keypose arc (`clamber_builder.py`, reproducible in `M5_authoring.blend`): `Jump_Run_appex` f1 hang → `Jump_Run` f9 **hook** (forepaws swing to hip height, 34 uu forward = paws over the lip) → `Jump_Run` f7→`Land_run` f5 pull (body rises past the planted paws) → `Land_run` f5 hind-clear (all four gathered under the body) → `Land_run`/`Idle_Base` @0.45 settle. Ends on the settle, **no push-off extension** (the start-step lesson) and near the `Land_stop` pose the exit actually enters. **Two authoring notes specific to this verb:** (1) **no §B2 crouch table needed** — unlike pivot/skid/start, the mantle's vertical travel comes from the component moving the CAPSULE, so body height is already carried; Spine translation is held constant so Blender preview == UE render; (2) **no IK bake** — every frame is airborne, and the airborne rule ("bake targets = the authored pose's own tips") makes it a true no-op. **KNOWN STUB LIMITATION:** the forepaws do not counter-animate the capsule rise, so hooked paws drift up with the body instead of pinning to the lip; exact compensation is impossible in one clip because the rise scales with ledge height (25–70 uu band). Polish = procedural paw-pin in C++ during `bGoMantle`, or height-bucketed clips. **Two PIE sessions, 15 mantles, ledges 27–69 uu, ZERO aborts** — every takeover that armed completed, scrub monotonic 0→1 every time. Second session ran at `Slomo 0.5` and the takeover **stretched cleanly** (109 samples instead of 55, still monotonic, still landing exactly on 1.0) — `MantleElapsed` accumulates dilated DeltaTime, so the curve tracks world time rather than desyncing; a mantle during the 0.2-dilation match-end Warning phase will behave. **The known-weak part is the ANIM, not the mechanics** — one clip plays for a 2.5× range of capsule rise, so off-nominal ledges read as a mismatch between animation and on-screen action (bug-bash BB-27; the fix shape is the pivot's 90/180 precedent — height-bucketed variants selected by a ledge height latched at `StartMantle`). **Transitions:** entry on `bGoMantle` from Jump_Fall/Jump_Apex/Jump_Launch/Move/Idle (0.10); exit `Mantle → Jump_Land` on `!bGoMantle && Anim_JumpPhase != Fall` (0.10) and `Mantle → Jump_Fall` on `!bGoMantle && == Fall` (0.15) — exhaustive by construction, and the successful-mantle path funnels through the already-hardened Jump_Land entries.

**Wall Bounce — verb 2, SHIPPED 2026-07-24, Sean-approved 2026-07-25 after two tuning rounds.** A jump press while airborne next to a wall kicks off it instead of being a dead input. **Not a takeover** — no movement mode change, no CMC apply/restore, no traversal state: a single `LaunchCharacter(Normal × `WallBounceLateralSpeed` 420 + Up × `WallBounceVerticalSpeed` 620, XY+Z override)` that hands straight back to falling physics, which is why it can safely interrupt anything. Both planes are **overridden, not additive** (an additive kick off a fast fall barely registers). Detection is the shared `ProbeWalls` helper at **4 directions** (`WallBounceReach` 40) vs the mantle's 1 — pressed into a corner or a chimney the wall you want is rarely the one you face, and alternating-normal bounces give chimney climbing for free. `DoWallBounce` re-enters `JumpPhase::Launch` (the Fall case has no "started rising" edge, so without it the cat sails back up still in the fall pose) and **resets `JumpAirTime`** (`JumpRiseProgress` scrubs the launch clip by it — a bounce late in a long fall would otherwise start the clip already finished); `bLeftGroundByJumping` deliberately stays true so a bounce never hands back coyote time. Hooked into `OnJumpInputPressed` **and** the per-frame jump-buffer retry, so a slightly-early press still kicks (`CanJump()` is false airborne, so the bounce has to be tried before it). MP = the pivot-braking mirror pattern: owner launches immediately, `Server_WallBounce(FVector_NetQuantizeNormal)` sends **the wall normal, not the velocity**, so both machines derive the launch from the same knobs. Per-bounce log line = the plant-and-spring authoring spec. No new anim — a bounce re-enters `Jump_Launch`, which at bounce speeds plays the Run branch (`A_Cat_Jump_RunStart`) scrubbed by `JumpRiseProgress`; the real sideways plant-and-spring clip is the traversal batch.

**Wall-bounce tuning round 1 (2026-07-24) — Sean: "fighting the mechanic to keep the cat going up."** PawPrint found THREE compounding causes, all fixed together; none of them was the launch magnitude, which is why raising it alone wouldn't have worked. (1) **`FallingLateralFriction` was a bare constructor write of 3.0** (UE default 0) — measured the kick decaying 397 → 215 cm/s in 0.1 s. Now an exposed `MovementFallingLateralFriction` UPROPERTY **on the BeginPlay re-apply list** (it had the classic constructor-only trap), and the bounce drops it to `WallBounceReboundLateralFriction` 0 for its window. (2) **The player's own approach input cancels the kick** — you must hold *into* a wall to reach it, worth about −70 cm/s over the first 0.2 s. `Move()` now cancels only the **into-the-wall component** during `WallBounceReboundTime` (0.15 s at the time; **ships 0.25** — see round 2) (deliberately NOT a blanket input lock — that would fix the rebound by deleting the air control the same feedback asked for more of). (3) **THE BIG ONE — the gravity interpolator carried the fall value into the bounce.** `UpdateJumpGravity` snaps `GravityScaleInterp` on ground phases "so the next airborne jump starts from the correct baseline, not a stale fall value"; a wall bounce is a **mid-air relaunch**, the one case that comment never had to cover. Sitting at `GravityScaleFalling` 5.5 and ramping down over ~0.1 s, the first third of every kick's rise was fought by 2–3× the intended gravity — telemetry showed apex at **+0.22 s instead of +0.32 s**, cutting peak height ~98 → ~60 cm, which made each chimney cycle net roughly zero. `DoWallBounce` now snaps the interpolator (and `GravityScale`) to `GravityScaleRising`. **Lesson worth generalizing: any future verb that relaunches mid-air must snap the gravity interpolator** — scramble and curtain-climb exits both qualify. Air-control authority (`JumpAirControl 0.7 × MovementAcceleration 500` = **350 cm/s²**, vs the UE third-person template's 717) and `WallBounceLateralSpeed` are the two knobs deliberately left untouched pending a re-feel.

**Wall Attach — the shared cling/scramble state, SHIPPED 2026-07-24, Sean-approved 2026-07-25.** Sean's read after the bounce tuning: *"in Jedi it feels like Kal sticks to the wall he bounces to and then I have to press jump again… right now it's a bit herky-jerky and I'm almost spamming the jump button."* Diagnosis: the bounce is a pure **impulse** with no dwell, so the wall only exists for the frame the probe catches it and the player must synchronise with the arc — telemetry showed apex at +0.30 s and chimney kicks at ~0.41 s intervals, i.e. a target window barely wider than the 0.15 s jump buffer. A cling removes the timing requirement entirely and hands the tempo to the player. **Design call: cling and Vertical Scramble (verb 3) are the SAME state machine** — scramble is cling entered with an upward velocity budget instead of a downward slide, with identical exits — so they were collapsed into one `ECatTraversalState::WallAttach` rather than built twice. Verb 3 now reduces to its own detection (sprint entry speed, tall/tagged wall) + the top-out→mantle handoff. **Vertical profile from entry parameters:** RISE (scramble only, `Vz` eases `RiseSpeed`→0 over `RiseTime`) → CATCH (`WallClingCatchTime` 0.15 s, Vz pinned to 0 — the "stick" beat) → SLIDE (`WallClingSlideSpeed` 70). Cling enters with RiseSpeed 0 and starts at CATCH. **NOT a movement-mode takeover** — the cat stays in `MOVE_Falling` and the state constrains velocity per tick, so `Landed()`, the jump SM, the cushion and foot IK all keep behaving and the state can be entered/dropped on any frame with no CMC apply/restore pair to get wrong (contrast the mantle's `MOVE_Flying`). **`WallClingMinApproachSpeed` 20 doubles as the anti-re-stick guard** — right after a kick the cat travels *away* from the wall it left, so that wall fails the closing-speed test by construction and only the wall being approached can catch; the 0.12 s `WallAttachCooldown` is just a backstop for the one frame before velocity flips. Exits: jump → `DoWallBounce` **off the held normal, not a re-probe** (in a chimney both walls are usually in reach, and the player already chose this one); `WallClingMaxTime` 1.4 s; wall lost; grounded; grabbed; **mantled** (round 3) — and nothing else (the away-release that shipped here was removed in round 2, below). Detection runs **after** `TryDetectMantle` so a reachable ledge always outranks sticking to the wall under it. MP = the mantle model: `Server_SetWallAttach(bActive, Normal, RiseSpeed, RiseTime)` mirrors both edges reliably and the server runs the same deterministic profile — no streaming. `bGoWallAttach` replicated `COND_SkipOwner`; no ABP consumer yet (the wall-hug clip is traversal-batch work), PawPrint channel `WallAttachPhase` (1=rise / 2=catch / 3=slide).

**Wall-attach round 2 — STICKY CLING + crossing crispness (2026-07-25, both Sean-approved: "feeling a lot better").** Two independent fixes from one PIE round. (1) **The away-release is DELETED** (`WallClingReleaseAwayDot` gone, not defaulted to 0 — a knob whose only correct value is "off" is a trap for a later session). Sean's report: clinging to the left wall and holding D to aim at the right wall dropped the cat instead of arming the jump. **The geometry is the whole lesson: in a chimney the wall you are aiming AT lies along the held wall's own normal**, so "steering away" and "expressing intent to cross" are the same input vector — the release fired on the exact frame the player committed, and the kick it was supposed to enable never happened. This is the Celeste/Ori/Jedi convention (jump press alone decides when to leave; direction steers the arc afterward, and holding away notably does NOT let go); Uncharted is the *other* family — handhold-to-handhold jumps require stick direction because there direction CHOOSES the target, which a chimney kick does not. The kick path never consulted input to begin with (`TryWallBounce` uses the held `AttachNormal`), so only the cling needed the change. Cost accepted: no voluntary let-go — you kick, time out at `WallClingMaxTime`, land, or lose the wall. Verified next round: **53 attaches, 53 kicks, 100% conversion, zero self-releases** (was 5 unexplained drops in 25 s). (2) **`WallBounceReboundTime` 0.15 → 0.25 — this, NOT `WallBounceLateralSpeed`, is the crossing-crispness knob.** Sean read the bounce as "needs a bit more distance"; PawPrint showed the opposite of a reach failure — **49/49 crossings connected**, traverse clustered 113–123 cm — but the kick left at 420 cm/s and **arrived at 81 (19%)**: 62 cm covered inside the friction-free rebound window, then 55 cm bleeding out over twice the time, so the far half of every crossing was a drift. Raising launch speed cannot fix that shape — post-window reach asymptotes at `v0/FallingLateralFriction` (420/3 ≈ 140 cm), so more speed just makes the already-fast half faster while the mushy tail survives further out; it also steepens the kick against the fixed 620 vertical and moves height-per-cycle, which was already approved. **Generalizable: when a launch "feels short", measure the arrival speed before touching the launch magnitude — a decay problem and a reach problem present identically on screen.** (3) **Every attach release now logs its reason** (`EWallAttachEnd`: kick / timeout / wall lost / grounded / grabbed / remote / aborted) — round 1 could only identify the away-release by *eliminating* the other exits from duration data. Same doctrine as `ETraversalReject`: a state that can end several ways must say which. `MovementFallingLateralFriction` 3.0 (UE default 0, exposed in round 1) is still untouched and is a live candidate for a general air-feel pass — deliberately not folded in here, since it moves every airborne moment in the game, not just bounces.

**Mantle detection round 3 — the cling was eating mantles; detection re-aimed by HEADING (2026-07-25, Sean-verified at the system's far edge).** After the cling shipped, Sean: *"almost impossible to get a mantle without getting stuck to the face of the wall and sliding down."* Three causes, found over two PIE rounds, each a different lesson.

1. **The cling caught mid-rise and cancelled the rise.** 68% of catches (82% on the client) fired while still in `Launch`. The lip band is measured **from the capsule bottom**, so it is a window the cat passes *through* and vertical motion is what walks a lip into it; the cling's CATCH beat pins Vz to 0 and kills exactly that, then slides the wrong way. Fix = `WallClingLedgeSuppressSpeed` 50: the cling defers when the detector reports the out-of-band reject on the side the cat is **closing** — `LipTooHigh` while rising, `LipTooLow` while falling. **Shipping only the rising half was a half-written rule** and left the overshoot case open (a sprint jump that clears the ledge reads `LipTooLow` on the way down — telemetry caught a 650 cm/s jump with one frame of `LipTooLow` at 16.220 and a cling START on that same frame, then 1.4 s of sliding past the ledge to a timeout). Narrow by construction: a wall with no ledge reports `NoWall`/`NoLip` and still catches, so chimney bouncing is untouched.
2. **A cling BLINDED the mantle detector** — `TickComponent` returned right after `DriveWallAttach`, so `TryDetectMantle` never ran while attached (the 1.4 s hole above is visible in the `MantleReject` channel as missing samples). Detection now runs during an attach and releases it (`EWallAttachEnd::Mantled`) when a lip enters band, so a cling under a ledge *becomes* a mantle. **This is also the mechanism Vertical Scramble's top-out handoff rides** — a scramble is this state entered with a rise budget, and at the top the lip enters band. Note held input is the only heading source while clinging (horizontal velocity is zeroed there), so a cling→mantle needs the stick held toward the wall.
3. **The two detectors didn't look the same way** — mantle probed 1 ray from **actor forward** and required held input; the cling probed 4 and required none. At the catch frame the mantle read `no wall` 33% of the time and `no input` 27%: the cling was grabbing walls the mantle never examined. **Both obvious fixes are wrong.** Forward-only loses ledges the cat drifts toward but doesn't face (air control + camera-relative input pull heading and facing apart constantly — this was the real bug). Radial over-corrects: 4 rays plus the directionless `HasMovementInput()` gate — *any* stick direction satisfied it, a filter the forward probe had been supplying implicitly — fired ~15× too often (12 mantles in 38 s; Sean: "getting mantles when I didn't expect"). **Shipped: ONE ray aimed down the cat's HEADING** (held input, else travel ≥ `MantleMinApproachSpeed` 20). Aiming *by* intent rather than filtering *after* it also dodges the nearest-hit trap, where a radial probe hands back a side wall while the cat heads at the front one. `ProbeWalls` gained an optional basis direction; bounce and cling still fan 4 rays from forward, because they answer a different question ("is there a wall near me", not "is there a ledge where I'm going"). Everything downstream measures along the **wall normal**, and `StartMantle` snaps the body to face the ledge (derived from start→target so owner and server turn identically — the clamber clip is authored as a straight-ahead pull-up and would otherwise crab).

Verified at the far edge: a full 650 cm/s run-jump onto a 64 uu ledge (band max 70) armed on the **first frame** the wall entered probe range and mantled — `MantleReject` reads 7 (`no wall`) through the whole rise, then 0 (`armed`) for one frame. Session: 4/4 mantles as expected, zero clings, zero mantles stolen.

**Vertical Scramble — verb 3, SHIPPED 2026-07-25 (mechanics, Sean-approved over three tuning rounds).** Run at a climbable wall fast enough and the cat scrambles UP it. **Zero new state machine** — it is `ECatTraversalState::WallAttach` entered with a rise budget instead of a downward slide (the 07-24 collapse decision paying off), so it inherits every exit for free: jump kicks off the held normal, the budget decays into the cling's own slide, and a lip entering band at the top hands off to the mantle through the detection-during-attach path. MP is free too — `Server_SetWallAttach` already carried `RiseSpeed`/`RiseTime`. Tick precedence is now **mantle → scramble → cling** (a reachable ledge beats climbing the wall under it; a climbable wall run at speed beats merely hanging on it), each gated by `TraversalState`.

**GATED BY LEVEL AUTHORING — the first verb that is (Sean's call: "not every wall is scrambleable").** `IsScrambleSurface()` OR's two sources, evaluated only *after* a wall probe hits so the overlap query is rare rather than per-frame: (1) `ScrambleSurfaceTag` (`Scrambleable`) on the hit **actor** or on an individual hit **component** — component tags let one mesh of a multi-part actor climb while the rest do not; (2) the cat overlapping a volume tagged `ScrambleVolumeTag` (`ScrambleZone`), the broad override for blocking out a climbable shaft without touching meshes. Physical-material gating was considered and declined (needs art-pipeline discipline about material assignment). **The CLING stays deliberately ungated** — an ordinary wall means hang-and-kick, a marked wall means climb, which is also what keeps the tuned chimney bouncing working on plain untagged geometry. Test surfaces: `Cube9` + `Cube30` in TestMap_02 carry the tag.

**Entry + budget:** closing speed ≥ `ScrambleMinEntrySpeed` 450 (sprint band — a walk into a wall just stops; the run-up IS the entry, gated on speed rather than the sprint flag so height scales continuously), plus an unbroken wall face `ScrambleMinWallHeight` 120 uu above the contact point so a low block stays a mantle. Rise maps entry 450→650 onto **500→775 cm/s decaying linearly over `ScrambleRiseTime` 0.75 s**, so climb height = RiseSpeed × RiseTime / 2 and a harder run-up climbs higher (gait differentiation for free — the weighty-stops trick). Grounded entries switch to `MOVE_Falling` first or the attach's own grounded-exit fires on its first drive tick. The tall-wall probe starts OUTSIDE the face and traces in — starting inside returns a start-penetrating hit with a garbage normal (the 07-21 foot-IK trap).

**Three fixes from the tuning rounds, two of them real bugs:** (1) **`WallClingMaxTime` is charged from the END of the rise** (`AttachElapsed > AttachRiseTime + WallClingMaxTime`) — a cling budget spent on a climb left only 0.7 s of hang and dumped the cat mid-wall; a cling has RiseTime 0 so its 1.4 s is unchanged. (2) **A timed-out face stays spent** (`SpentWallNormal`, dot > 0.9, cleared on ground / kick / mantle) — the player is still holding into the wall, air control supplies closing speed, and the cat re-gripped ~0.12 s later, which made the timeout meaningless and read as the "detaches then reattaches" hitch; clearing on kick is what keeps alternating-normal chimneys working. (3) **Height is now MEASURED, not estimated** — attach-end logs `climbed N uu` and a `WallAttachClimb` PawPrint channel samples live Z gain. Worth knowing: achieved climb tracks the arithmetic within **~4%**, because Vz is rewritten every frame so gravity only gets one frame to bite. Tuning went 750/0.55 s ≈ 200 uu peak (too low) → 900/0.85 s ≈ 370 (too high) → **775/0.75 s ≈ 290** (shipped). Height was taken out of the DURATION rather than the speed: a slower climb over the same time read sluggish where a shorter one stays punchy. **No anim** — `bGoWallAttach` still has no ABP consumer, so the cat climbs in a fall pose; the scramble loop clip is traversal-batch work and each climb logs its entry→height spec. Fence Trot followed and turned out **not to be a verb at all** — see the balance-assist bullet below.

**Balance assist — verb 4 attempted as Fence Trot, SHIPPED as NOT A MODE (2026-07-25, Sean's call).** Walking a fence rail or block-wall top needed no state, no takeover and no replication in the end — and getting there took three rebuilds, each teaching something.

**It began as a mode** (`ECatTraversalState::FenceTrot`): speed clamped to 150, input projected onto the edge axis, position magnetised to the centreline. It worked, and it was **boring** — Sean: *"it's not like I'm playing a balancing game, it's just locking the cat into a forward or backward slow walk."* Telemetry convicted it: **97% of frames pinned within 3 uu of centre at a mean speed of 96.** The design took away speed, steering and lateral position and gave nothing back. **Deleted entirely** — the state, the `EFenceEnd` enum, `Server_SetFenceTrot`, the clamps, the input projection, the entry-alignment gate and the exit grace all went. What survived is the geometry.

**What ships is a stateless assist** (`UpdateBalanceAssist`): find a narrow surface, blend a small lateral correction toward its centreline, otherwise leave the cat completely alone. Three consequences, and they are the argument for the shape: (1) **no replication surface** — the correction derives purely from world geometry and the pawn's own position, so owner and server compute it identically with **no RPC**, no mirrored edges, and none of the "dropped edge strands the server" failure mode every other verb designed around; (2) **it composes** — sprinting, skidding and pivoting on a wall all just work, where the mode had to suppress all four grounded systems by clamping under their entry thresholds (which was also the ONLY place a traversal verb contended with the grounded CMC precedence chain — that risk is now gone); (3) **falling off is texture, not a tax.** Knobs (`Traversal|Balance`): `FenceAssistStrength` 4, `FenceAssistMaxSpeed` 50 (≈7% of the cat's lateral authority at a 400 walk — an assist cannot hold a line, only catch drift), `FenceAssistBlendRate` 6, `bScaleAssistByNarrowness` (full help on a rail, **zero** by `FenceMaxSurfaceWidth` 60 — a wide wall top should feel unassisted). Detection stays IMPLICIT: no tags, no volumes, because a narrow surface announces itself geometrically — the exact opposite of the scramble's authored gate, where a climbable wall looks like any other.

**Two bugs worth remembering, both of which presented as bad feel:**
1. **A detector must not depend on a quantity its own mode changes.** The first build probed across the cat's *right vector* — but engaging balance mode rotated the cat, which rotated the probe, which failed, which exited, which rotated it back: a 1-2 frame enter/exit oscillation, **120 events in one session**, felt as "control input doesn't match the action". Fixed by deriving the surface axis from a **ring of support samples in WORLD directions** (`FindBalanceAxis`, 12 rays, doubled-angle circular mean — doubled because a surface direction is a LINE, so opposite samples must reinforce rather than cancel). Same family as the mantle-vs-cling bug earlier the same day: both looked like tuning and were feedback paths.
2. **Measure quantisation before tuning strength.** With the assist live, Sean read it as slightly too weak. The offset histogram had a **hole** in it — 45% of frames at exactly 0, 50% at exactly 6.67, and *nothing between* — because the centre offset was the midpoint of two sample indices and could only land on a Step/2 grid. That is a **±3.3 uu dead zone** where the assist did nothing at all, then jumped a whole step: an assist that stutters, not one that is weak. Raising strength against a quantum only makes the steps bigger. Fixed by **bisecting the real edges** (4 iterations between the known supported/unsupported bracket ≈ 0.8 uu). Verified against Cube25: measured offset now tracks true drift within **±0.4 uu**, and span reads the exact true widths (20.0 / 25.0 / 45.0, previously 13.3 / 26.7 / 40). Post-fix: median offset 2.08 uu, 57 distinct values, ~41 s walked on Cube25.

Also burned in: `FenceProbeHalfWidth` (80) must clear half of `FenceMaxSurfaceWidth` by a real drift margin — it shipped at 45 against a 60 max, so a flank sample landed ON the surface after ~23 uu of drift and detection rejected while the cat was still comfortably on the rail. And the centreline correction is `+CentreOffset` (the probe reports where the surface centre sits relative to the CAT); the inverted sign shipped once and shoved the cat off the rail it was meant to hold. **Level authoring:** `Cube25` in TestMap_02 is the fence/wall stub — 3250 × 25 × 400, top at z 320 — and 25 uu is narrower than the cat's own capsule (radius 14), which is fine: 20 uu is proven walkable.

**Traversal anim batch, clip 1 — `A_Cat_Wall_Hang` + the `WallHang` ABP state (2026-07-25, Sean-accepted: "isn't perfect by any means but it gets the job done").** The first traversal clip, and the first clip in the project authored **from scratch** rather than assembled from kit keyposes — the AnimX kit has 85 sequences and **zero wall or climb clips**, so M5's donor-assembly approach did not transfer. Plan: `Saved/.Aura/plans/traversal-anim-batch.md`.

**Authoring (Blender, `M5_authoring.blend`, action `WALL_HANG`, 1.167 s / 36 f / loops):** body pitched −88° about X at the **Spine** bone (rotation survives retargeting; the pitch is baked into the clip, NOT procedural — a wall pose is a *silhouette* composed as a whole, where a near-normal pose pitched 90° procedurally reads as a walking cat rotated sideways; procedural pitch stays right for ground *slope*, which is a continuum of small angles). Limbs IK-solved to paw targets on a wall plane with `chain_count=3` so the scapula pose survives, then baked to FK and **all 147 location fcurves stripped** — verified 0.0000 cm pose drift, so Blender preview == UE render. Round-trip verified to the hundredth of a cm in UE.

**The anatomy that makes it read as a cat:** (1) **scapular elevation** — cats have no clavicle, the blade floats in muscle, so a cat hanging by its forelimbs sinks between its shoulders and the blades ride up past the spine line (+10.4 cm measured). If one detail sells it, this is it. (2) **Asymmetric forepaws** (z 80 / 74) — a symmetric hang reads as a rug pinned to a wall. (3) **Forearms flat up the wall**, elbow low and near the face, upper arm angling back to a shoulder 18 cm off it — that fell out of the IK solve and matches the real animal. (4) **Hinds folded to 59% extension, knees splayed** — a cat on a wall is a coiled spring, not dead weight. (5) A **slip and re-grip** beat: the trailing paw drags down 3.5 cm with claws raking, the head snaps to it, then it slaps back up *higher* than it started. **Known limits:** timing/arcs are default bezier and reference-free (anatomical reasoning, not observation — Sean is sourcing reference for the next clip); and the cat **cannot sag under load**, because translation is discarded, so strain is expressed as scapular pump + spine flex. A real weight-sink needs a procedural mesh-Z drop (the §B2 pattern).
