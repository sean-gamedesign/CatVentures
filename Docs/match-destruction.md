## Match Flow: the Chaos loop

Server-authoritative match state machine living in `ACatGameMode`, replicated to clients via `ACatGameState`.

**The one and only GameMode Blueprint is `GM_CatVentures` (`/Game/Core/GM_CatVentures`)** — it is both the global default (DefaultEngine.ini) and the TestMap_02 World Settings override. It assigns `DT_ChaosRewards`, `PrimeCatBase` as the pawn, BP_CatPlayerController/BP_CatGameState, and `ChaosThreshold = 100`. (A duplicate `BP_CatGameMode` with a broken pawn class was deleted in the 2026-06 cleanup — don't recreate it.)

**Data-driven scoring** (do NOT hardcode prop scores):
1. A breakable prop (component Blueprint `BPC_ChaosItem` on `BP_Destructible_Base`) carries an `FName ChaosRewardKey` naming a row in the `DT_ChaosRewards` DataTable (rows are `FChaosRewardData`). The prop stores only the key, not a score.
2. On break (OnChaosBreakEvent → `Native_Shatter`) it calls `ACatGameMode::ReportItemDestroyed(Item, Location, Key)` (server only — the GameMode cast naturally fails on clients) and `RegisterDebrisActor` on the local PlayerController (every machine).
3. GameMode does `ChaosRewardTable->FindRow<FChaosRewardData>(Key)` to resolve `ChaosValue` + `DisplayName`. A missing/`None` key falls back to `DefaultChaosValue`.
4. `TotalChaosScore` accumulates and is pushed to `ACatGameState::ChaosScore` (replicated; `ChaosThreshold` is pushed once in `BeginPlay` so clients compute `GetChaosPercent()`).
5. At `TotalChaosScore >= ChaosThreshold`, GameMode latches `FinalBreakLocation`/`FinalBreakActor` and starts the match-end phase sequence.

> ⚠ **`ChaosThreshold` is currently a DEBUG VALUE: 1,000,000 (design value: 100).** Set 2026-08-16 so the match-end sequence would stop firing during Objective System testing. **The match-end loop is therefore effectively disabled** — smashing the whole map will not trigger Warning/FinalCut/Fade/Aftermath. If you are debugging "the match never ends", this is why. Revert `ChaosThreshold` to **100** on `GM_CatVentures` (`Match|Tuning`) to restore it. Tracked in `Docs/objectives.md` under the live test scaffolding.

**Phases** (`ECatMatchPhase`): `Playing → Warning` (slow-mo, movement stripped via `IMC_LookOnly`, look preserved) `→ FinalCut` (cinematic camera on break location) `→ Fade` (fade-to-black with a real-time settle hold) `→ Aftermath` (orbit/director-cut cameras over the densest debris cluster + scoreboard). GameMode drives transitions and calls `Client_OnMatchPhaseChanged(Phase, Location, TargetActor)` on every PlayerController — the RPC carries the value to dodge a property-replication race.

**Client cinematics** live in `ACatPlayerController`: `HandlePhase_*` methods plus `BlueprintImplementableEvent`s `OnMeowTimeTriggered`, `OnCinematicTakeover`, `OnShowScoreboard`. The Aftermath director frames the densest debris cluster (chunk-centroid math with abyss/floor filters); tunables are the `Match|Tuning` UPROPERTYs. Each client tracks its own broken props via `RegisterDebrisActor`. The orbit tick measures real elapsed world time (not a fixed 1/60 step).

**Rematch**: `ACatPlayerState::bWantsRematch` (set via `Server_SetRematchReady`, only honored during Aftermath); `ACatGameState::AllPlayersReadyForRematch()` gates the host's Play Again button **in WBP_RaidScoreboard** (Branch before `Host_ServerTravel("?Restart")`). `PlayerScores` is currently an MVP even-split of the total across `PlayerArray`.

## Destruction: Chaos Geometry Collections

Breakable props are Unreal **Geometry Collections** (`UGeometryCollectionComponent`) simulated by the **Chaos** solver. Note the name collision: the *physics* "Chaos" solver vs. the *gameplay* "Chaos score" above are different things.

**The destruction model (Phase B, 2026-09-13, Sean's call):** walking or trotting into a prop **bumps** it and leaves it intact; **charging** into it (horizontal speed ≥ `ChargeShatterSpeed`, 500 cm/s — trot 400 leaves it, sprint 650 smashes) shatters it on contact; a **swat** shatters it (4th hit); a **hard impact** from another object shatters it per the DataTable row. Once shattered, the debris is **bulldozed** out of the cat's path rather than obstructing it. All tunables live on `ACatBase` under `Physics Bumper|Bulldozer` (`BulldozerRadius` 110, `BulldozerPushStrength` 5000, `BulldozerMinSpeed` 60, `ChargeShatterSpeed` 500).

Three break paths, all funneling into `ForceShatterGC` (deterministic, bypasses the asset's Damage Threshold) and fracturing **locally on every machine** via multicast:

1. **Charge** (C++, `ACatBase::UpdateBulldozerPush`): a per-tick sphere overlap **QUERY** (`OverlapMultiByObjectType` on `ECC_Destructible` + `ECC_PhysicsBody`, radius `BulldozerRadius`) on the cat's owning machine finds an intact GC while the cat is at/above `ChargeShatterSpeed` → `Server_BumperHitGC` (or the multicast directly on the host) → `Multicast_BumperHitGC` → `ForceShatterGC` on every machine's solver. **The PhysicsBumper's overlap-EVENT path (`OnBumperOverlapBegin`) is DEAD for Geometry Collections** — GC components emit no begin-overlap events at all (2026-09-13 diagnosis: zero bumper overlaps even on a sprint). The event branch is kept, shares `ChargeShatterSpeed`, and would only ever fire for a GC that does emit events; the query is the path that works.
2. **Swat accumulation** (BPC_ChaosItem): `OnTakePointDamage` (server) counts swats; the **4th swat** triggers `Multicast_TriggerShatter` → `ForceShatterGC`. Earlier swats apply `Multicast_ApplySwatImpulse` knockback (ShotFromDirection × 800, bVelChange).
3. **Hard impact** (BPC_ChaosItem): `OnComponentHit` (server) → `ACatGameMode::ShouldImpactShatter` → `Multicast_TriggerShatter`.

   **Corrected 2026-08-16:** this doc previously said "component velocity > 600". The graph was verified directly and said **1200**, not 600 — and the quantity itself was respecced. Non-Heavy props still gate on the victim's own speed (threshold now `DefaultImpactVelocityThreshold`, or a per-row override); **Heavy props measure the impactor instead**, because a high-mass prop struck by a light one barely moves and would never break. Per-prop thresholds and the Heavy flag live on `DT_ChaosRewards` — see `Docs/objectives.md` for the tier, the two-named-columns rule, and the verify-in-build logging that will pick between `NormalImpulse` and mass×speed.

   **The bumper path refuses Heavies** (`Multicast_BumperHitGC`, gated there because the listen-server host calls the multicast directly and would bypass a server-only check) — but that gate is **currently INERT**: it tests a `HeavyProp` actor tag that nothing sets yet.

**A Geometry Collection SURVIVES its own fracture** (BB-17): the clusters break but the component and actor live on — they must, since the debris *is* that component and `RegisterDebrisActor` retains it. So a break path can fire more than once for one prop, and anything counting destructions must latch (see `Docs/objectives.md`).

### Debris policy — the fracture-romp fix (Phase B, shipped `380d04b`, 2026-09-13)

Walking into fresh debris **was broken** (measured 2026-08-16, the MeowTime spike): the capsule got stuck inside chunks and the CMC's depenetration snapped it out (read as teleporting), wall-attach clung to chunks because `ProbeWalls` could not tell a chunk from a wall, and foot IK railed at its ±25 clamp because every probe landed on a different chunk height. None of it was time dilation — all three were *more* frequent at normal speed. Fixed in three layers, built via Live Coding in one session and then full-rebuilt:

- **Layer 1 — collision flip on fracture** (`ForceShatterGC`, runs on every machine because it is the multicast target): the moment a prop shatters its GC component goes **Pawn → Overlap** (no more capsule stick/teleport), **Visibility → Ignore** (ProbeWalls and the foot-IK probe stop reading chunks as walls/floor), **Camera → Ignore** (the boom stops popping on flying debris). `WorldStatic`/`WorldDynamic`/`PhysicsBody` stay Block so chunks still pile on the floor and each other. **Intact props are untouched** — they only reach `ForceShatterGC` on shatter, so they still block and smash normally. Because Layer 1 only touches `ECC_Pawn`/`ECC_Visibility`/`ECC_Camera`, the swat sweep and grab sweep (both object-type queries on `ECC_Destructible`/`ECC_PhysicsBody`) still find debris — verified in source, not assumed. **Consequence to know:** a chunk can never generate a capsule `OnComponentHit` any more, so debris never reaches the impact-response classifier (see `Docs/impact-response.md`) — the 09-12 "GC chunks fire zero impacts" observation is now the intended behaviour, not a defect.
- **Layer 3 — GC reject in the probes** (belt-and-suspenders over Layer 1, and it also covers *intact* props): `UCatTraversalComponent::ProbeWalls` skips any `UGeometryCollectionComponent` hit outright (not even counted as "a wall near me", so bounce/cling detection ignores props and debris cleanly — you cannot wall-cling to a vase either), and `UpdateFootIK` treats a GC hit as a miss, same shape as the wall-pin start-penetrating filter.
- **The bulldozer** (`UpdateBulldozerPush`, same per-tick query as the charge path): fractured debris (Pawn=Overlap is how the query tells intact from fractured) is shoved out of the moving cat's path **per chunk**, radially away from the cat, via `AddImpulseAtLocation` at each chunk's live position. The positions come from **`GetComponentSpaceTransforms3f()`** transformed by the component transform — NOT `GetCurrentTransforms()`, which returns raw hierarchical locals and put most chunks out of range while landing a few impulses on far chunks by accident ("close clip, far impact"). The proxy impulse is mass-scaled (no velocity-change mode), which is why `BulldozerPushStrength` is a large momentum number. Five push mechanisms were tried before this one (uniform LinearVelocity field, wake-only, three guessed proxy samples, per-chunk on the wrong transforms) — don't re-derive them. Non-GC physics props take a single mass-independent `AddImpulse` (`bVelChange`, capped 1500) on authority only.
- **The sleep wall** (the session's big time sink): settled Chaos chunks **sleep and drop out of the overlap query**, so nothing could find or push them — "the cat clips through, closest-to-start chunks worst". Fix, Sean's pick: `Config/DefaultEngine.ini [SystemSettings]` raises `p.Chaos.Solver.Sleep.Defaults.SleepCounterThreshold` from 20 to **900** (~15 s at 60 fps) so debris stays pushable for a window after it settles, then sleeps normally. `WakeAllRigidBodies()` alone was not enough.

**KNOWN OPEN — client scatter parity (Phase B follow-up, next task as of 2026-09-13).** The *fracture* is networked (`ForceShatterGC` runs on host and client, log-confirmed), but `UpdateBulldozerPush` gates GC pushes on `IsLocallyControlled()`, so only the machine driving the cat scatters its local chunks — the remote copies of that cat (on the host and on other clients) push nothing. A remote player therefore sees props **fracture in place ("cracked, not destroyed")** without scattering. Two candidate shapes, not mutually exclusive: (a) a one-shot radial scatter impulse inside `ForceShatterGC` itself, so every machine's fracture scatters at the moment of the break; (b) let the per-tick GC push run on *every* role using the proxy's replicated velocity — chunks are local on every machine anyway, and only the charge-shatter branch (which fires RPCs) needs the owner gate. Findings → gate before either is built.

Fracture is simulated **locally per client** (the trigger is multicast, not the resulting chunks), so debris differs slightly per machine — hence the Aftermath camera uses per-client `RegisterDebrisActor` lists, not replicated chunk transforms. `ApplyExternalStrain` is a no-op on plain Static Mesh Actors (no cluster graph). The swat count (4) is hardcoded in the BPC_ChaosItem graph; the hard-impact velocity threshold is `ACatGameMode::DefaultImpactVelocityThreshold` (1200) or the row's `ImpactVelocityThreshold` override, per the 2026-08-16 respec above.
